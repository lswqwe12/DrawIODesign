这份 `architecture.md` 写得非常扎实，完全吃透了 `spec.md` 的核心约束，并且把 Next.js 15 App Router 的目录结构梳理得很清晰。**整体没有架构级的硬伤，可以直接作为开发蓝图使用**。

不过，站在“落地执行”的角度，我发现了 **5 个潜在隐患和 3 个缺失的细节**。如果不提前修正，等写到 Phase 2/3 时可能会遇到难以调试的坑。

以下是具体审查意见和修正建议：

### 一、关键架构隐患（需立即修正）

**1. 多标签页支持与 `DiagramContext` 的单例冲突（⚠️ 高优先级）**
`spec.md` 第 3.1 节明确要求“支持同时打开多个设计文件（多标签页）”。
但你的架构中，`DiagramContext` 只保存了单一的 `chartXML` 和 `latestSvg`。这意味着如果用户打开两个文件，切换标签页时，当前编辑器的 XML 会被覆盖，极易导致未保存内容丢失。

- **建议修正**：`DiagramContext` 应该维护一个 **`Map<fileId, diagramState>`** 或 **标签页数组**，而不是单一变量。`useDrawio` 的 `loadDiagram(fileId)` 应切换当前活跃的 `fileId`，并恢复对应的 `chartXML`。

**2. XML 保存与片段的“生命周期陷阱”（⚠️ 高优先级）**
你规定“AI 只生成 `<mxCell>`，宿主负责包装骨架”，这非常正确。但有一个致命细节：**`onAutoSave` 和 `onSave` 拿到的 `data.xml` 一定是完整骨架，而不是 AI 片段**。
如果你的 `useDrawio.loadDiagram` 将包装后的完整 XML 传给了 DrawIoEmbed，那么后续 `onSave` 事件返回的一定是完整 XML。**千万不要在保存时再次调用 `wrapXml`**，否则会发生 XML 双重包裹（`<mxfile><mxfile>...`）。

- **建议修正**：在 `DiagramContext` 中维护一个 **`isAIGenerated`** 标志位。保存时直接存储 `onSave` 回调中的原始 `data.xml`（已是完整格式），仅在**首次加载 AI 片段**时执行 `wrapXml`。

**3. Next.js API Route 的 Body 限制（⚠️ 中优先级）**
`/api/ai/interpret` 需要接收 Base64 格式的 PNG 图片（`data:image/png;base64,...`）。Next.js 默认的 body parser 限制为 **4mb**，而一张稍复杂的 UML 图导出的 Base64 字符串可能超过 5-10mb。
如果不修改配置，AI 解读功能会直接报 `413 Payload Too Large`。

- **建议修正**：在 `next.config.mjs` 中增加配置：
```javascript
export default {
  api: {
    bodyParser: {
      sizeLimit: '10mb', // 或 '20mb'
    },
  },
};
```

**4. 文件列表与文件夹树的 UI 布局冲突（⚠️ 中优先级）**
Spec 2.1.1 说“左侧：文件夹树；右侧：文件列表”，但 Spec 5.1 整体布局是“左：文件管理器（含树+列表） | 中：编辑器 | 右：AI面板”。
你的目录将 `FolderTree` 和 `FileList` 平级放在 `FileManager` 下，但缺乏一个统一的 **侧边栏容器（Explorer View）**。

- **建议修正**：在 `src/components/FileManager/index.tsx` 中，将两者组合成 **上（树）下（列表）** 的经典 VS Code 风格，而非左右平铺。树形结构在最上方展示文件夹，点击文件夹后，下方列表刷新文件。

**5. `useDrawio` 与 `DiagramEditor` 的职责边界模糊**
你说“useDrawio 是唯一门面”，但 `DiagramEditor.tsx` 需要渲染 `<DrawIoEmbed>` 并绑定 `onLoad`/`onSave`。如果 `onSave` 的逻辑写在 `DiagramEditor` 里，它可能会绕过 `useDrawio` 直接修改 Context。

- **建议修正**：`DiagramEditor` 只负责 **渲染** 和 **事件转发（emit）**。具体的事件处理逻辑（如调用 fileService 保存）应当作为回调函数通过 props 传入，或者在 `useDrawio` 内部定义好 `handleSaveEvent` 后暴露给组件。

### 二、缺失的目录/文件（建议补充）

**1. 缺少 XML 解析/包装工具（Utils）**
你提到了 `wrapXml`，但目录中只有一个 `lib/utils.ts`（给 shadcn 用）。需要明确新增：

- `src/lib/xml-helper.ts`：包含 `wrapMxCells(fragment)`、`unwrapDiagram(xml)`（用于导入时校验）、`isValidDrawioXml(xml)`。

**2. 缺少“导入文件”的解析器**
Spec 2.1.1 支持导入 `.drawio` 或 `.xml`。用户上传的是文件对象，你需要读取文本并提取中间的 `<mxGraphModel>` 部分。

- 在 `src/services/fileService.ts` 中增加 `importFromFile(file: File): Promise<string>` 方法，利用 DOMParser 提取 XML。

**3. AI 面板的“流式输出”状态类型缺失**
`useAI` 和 `aiService` 需要处理 ReadableStream。建议在 `src/types/ai.ts` 中定义：

```typescript
export interface AIStreamChunk {
  type: 'start' | 'content' | 'end' | 'error';
  content?: string;
  xml?: string; // 如果是生成图表，最后会带一个完整的 xml 片段
}
```

### 三、版本锁定的一个小建议

你锁定了 `Next.js 15.1.6`，但 `react-drawio` 的 `^1.6.x` 版本在 Next.js 15 的严格模式（Strict Mode）下，iframe 的 `onLoad` 可能会在开发环境触发两次，导致编辑器闪烁。这是已知 issue。

- **建议**：在 `next.config.mjs` 中临时关闭 React Strict Mode 用于开发调试，或者等待 `react-drawio` 更新。如果不想关闭，请在 `useDrawio` 中增加 `useRef` 防重复初始化锁（`initializedRef`）。
